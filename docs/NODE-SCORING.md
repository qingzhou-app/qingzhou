# 节点多维打分择优 — 设计（v1，2026-07-07 拍板）

> 结论先行：**可行、有价值，但价值不在「维度多」，在三件事**——
> ① 稳定性维度避开「延迟低但抖动大」的节点（纯延迟择优最常见的翻车点）；
> ② 用你真实访问的域名当测量目标，分数反映真实体验而非 generate_204；
> ③ 倍率从「延迟相近才看」升级为连续成本项，流量成本可量化 → 直接支撑竞品对比宣发。

## build28 可用性保护（2026-10-15）

本批落实优先级1，评分权重与正常节点的8分/2轮黏性保持不变：

- VPN运行且开启代理精选时，只有本轮同一目标测通的候选才可替换选择。全失败、条件不足或轮次中断都保留原选择和既有连接；无原选择则不凭TCP结果发布“可用”节点。VPN关闭时仍可直连初选，报告明确出口未确认。
- 扩展回执区分内存/端口资源、节点转换、非法目标与临时内核/代理请求未完成。通信超时、旧扩展无分类回执均为条件不足，立即停止本轮、不清旧测量、不处罚节点。LibXray仍将启动与HTTP错误合并，因此不能进一步声称已定位密码、运营商、出口或站点根因。
- 现有绿色/UDP候选和无绿色前3规则保留；额外纳入当前节点作健康对照，不绕过地区排除。失败后最多增加2次请求，当前节点、初选节点优先，使用与主目标不同主机的统一备用目标。主/备用延迟不混排；仅全体主目标无成功时使用备用成功集。地区外当前节点若主目标成功，仍保持主目标优先，地区内备用结果本轮不替代它。
- 同一节点双目标失败，且本轮有仍然有效的成功节点作对照，才暂缓自动选择5分钟。按完整连接身份隔离，仅内存保存，不改用户排除项、不进云端。定时轮跳过冷却候选，但仍复核当前节点；手动择优/单节点复测可立即恢复。VPN启停或探测政策变化清空冷却，原地换出口保留冷却。当前节点满足本轮双失败条件且有可选择的测通替代时，绕过分数等待。
- 旧会话、用户选择变化、取消、手动重测、探测设置改变、候选删除/换身份/排除，会使旧轮失效。代理测量写回还核对单次轮号与完整身份。报告继续冻结真实测量计数和选择原因，选择不等于隧道已应用。

成本与边界：最多增加两次串行HEAD（每次5秒目标超时，另有启动/通信余量）；扩展38MB护栏保留，无额外下载测速。冷却不是网络分桶或永久故障认定，同一VPN会话内换Wi-Fi/蜂窝的样本隔离仍待下一阶段。真实环境/内存占用与延迟收益需真机验证，不能据自动化用例宣称已提速。离线回放当前仍只覆盖评分/分数黏性，尚未采集重放这些代理故障与复核事件。

下一阶段：网络上下文和样本时效、带宽近期窗口；之后是固定探测预算/轮换探索与真实连接反馈。多出口/按站点选择另属架构范围。

## build27 实现核对（历史基线，2026-10-14）

下文记录build27及更早v1历史设计；build28差异见上节。当前以`AppState.autoSelectBestNode`、`NodeScorer`和`NodeSelectionHysteresis`实际代码为准：

1. TCP节点每轮三次握手，取成功样本中位数（两个成功取较小值），最多8个节点并发；UDP节点不用TCP探针，需新鲜代理测量。手动排除/地区排除决定资格；优先地区有合格候选时限制候选池，否则全局择优。
2. 均衡档延迟/稳定性/带宽/成本权重45/30/15/10%；速度档60/25/10/5%；省流量档35/25/10/30%。倍率偏好关闭时成本权重为0，其余按比例归一。每维固定锚点0–100，避免节点池变化造成分数漂移。
3. 延迟维：TCP毫秒乘1.3再过锚点；有24小时内的代理值时，代理分70%+直连分30%。稳定性取最多100条本地历史的平均握手失败比例与直连延迟变异系数；样本不足3条给70中性分。这不是链路真实数据包丢包率，代理失败目前不记录为稳定性失败样本。
4. 带宽用真实会话当前节点的被动下行峰值，没有额外下载；缺值给60中性分。当前峰值只增不减，没有时间衰减/网络分桶；历史设计中的7天半衰期未实现，不能据设计文档宣称已具备。
5. 默认开启代理精选，但需要VPN运行且没有切换；优先测试直连低于200ms候选及UDP节点，无绿色候选则选直连前3。候选串行通过临时xray做HTTP HEAD。用户有至少3个常用代理域名时每轮轮换一个，否则使用默认Cloudflare或指定目标。只在本轮测通的候选里排名；全失败保留初选结果（该结果可能含历史代理分），不重新按纯直连排名。初选已存在时，未通过绿色门槛的更远TCP节点通常不参与精选。
6. scheduled路径且VPN运行/未切换时，同一挑战者对同一在位者总分领先至少8分、连续2轮才切；当前节点没有有效测量/被排除时绕过等待，手动择优也不等待。30分钟是默认择优周期设置，不代表每30分钟一定后台执行，iOS主App挂起时本机调度无法继续。实际生效必须由隧道回执确认，选择变化不等于已切换成功。
7. build27新增最近一次进程内报告，保存真实初选/精选的评分与候选池地区证据、连续轮保持原因、实际探测计数和中断原因。后来修改设置/测量不会重算历史报告；选择与VPN实际应用分开展示。取消/用户改变意图不发布旧选择，UDP未测不当作TCP失败。报告不进入本地配置或iCloud。

### 对比与优先改进（官方资料核对日期2026-10-14）

- [Surge URL-test](https://manual.nssurge.com/policy-groups/url-test.html)：代理HTTP HEAD，支持连接复用后的第二次请求计时、结果过期/网络变化后重测、毫秒容差。不是TCP ping最低；冷测与复用测延迟不能直接横比。
- [Surge Smart](https://manual.nssurge.com/policy-groups/smart.html)：真实连接首响应时间的时间加权均值、TCP重传惩罚、按站点近期成功/失败记忆，按连接选策略与重试；与轻舟目前全局单节点选择有结构差异。公开机制不等于我们做过竞品体验基准。
- [Stash策略组](https://stash.wiki/en/proxy-protocols/proxy-groups)：URL-test最低延迟及容差、当前失败即时切换，另有顺序fallback与负载均衡。
- [mihomo URL-test](https://wiki.metacubex.one/config/proxy-groups/url-test/)与[sing-box URLTest](https://sing-box.sagernet.org/configuration/outbound/urltest/)：目标URL、周期和切换容差可配置；不能把这些公开组的行为当所有客户端唯一算法。

轻舟优势是稳定性/倍率目标明确、固定锚点与回放可验证、被动带宽不烧额外配额，且测量身份/实际应用边界受回归保护。主要不足是全链路失败未形成可用性硬门槛、陈旧与不同网络样本混合、历史峰值/观测机会偏差、绿色筛选遗漏好出口、代理串行冷测成本、单目标偏差和缺逐连接/站点反馈。

以下为build27时的建议，优先级1已在build28实施有界保护；其余仍待后续：
1. 分清探测失败阶段（本机/扩展、目标站点、节点协议与出口），本轮全链路失败不要用TCP成功冒充已验证可用；复核后短暂降权/冷却，而不是一次失败永久禁用。所有候选失败时保留既有连接并明确未确认。
2. 按网络类型/会话分离样本，旧代理测量与稳定性数据按时间衰减，带宽用近期窗口/分位数而非永远最高值；未知倍率/带宽保持“不确定”，不能据此声称便宜或慢。
3. 使用“当前节点+评分前若干+少量轮换探索”的代理探测预算；连续领先按合理时间确认，降低30分钟两轮带来的恢复迟滞，iOS需明确扩展与主App职责。
4. 从真实连接反馈首响应/失败，再考虑按站点出口记忆。先完善采样质量和实验评估，再决定是否支持多出口；这属于另一个架构范围。
5. 回放与在线验证关注连接成功率、p50/p95首响应、切换次数、探测流量/电量及倍率配额，不仅比较总分。当前缺真实回放输入，不能宣称领先或量化提速/省流量。

## 0. 历史设计底账（2026-07-07）

现有算法 = **延迟单主维 + 倍率 tiebreaker + 地区硬约束 + 黏性滞后**：
- 全量测直连 TCP 握手 RTT → 「最快 ±30ms」视为相当（band），band 内选低倍率，同倍率再比延迟；
- VPN 运行中另有经代理精选（tieBand 200ms）；
- 换当前节点必须「快 ≥50ms 且降幅 ≥30%」（`autoSwitchWorthRestart`）。

可直接复用的按节点数据：直连延迟、经代理延迟、倍率（`rateForComparison`，未标注按 1.0）、
地区（名字/旗帜 emoji 解析）、被动带宽峰值（`observedPeakDownBps`，当前节点跑流量时顺带记录）。
**空白**：每节点只存最近一次测量（无历史序列 → 没法算稳定性）；无按节点的丢包/失败率留存。

## 1. 打分模型

`score(node) = Σ w_d × s_d(node)`，每维 `s_d ∈ [0,100]`，**锚点归一**（不随节点池相对漂移，可解释）。

| 维度 | 权重(均衡档) | 数据源 | 归一锚点 |
|---|---|---|---|
| 延迟 L | 0.45 | 经代理 + 直连**按分数混合**（2026-07-07 增强）：两者都有且经代理新鲜（≤24h）→ `0.7×score(经代理) + 0.3×score(直连×1.3)`，各自先过锚点归一再混合（不混原始 ms，量纲锚点不同）；只有经代理 → 全权重；只有直连 → ×1.3 惩罚；经代理 `lastProxiedTestedAt` 距今 >24h → 不参与（陈旧的经代理数字比新鲜直连更误导） | ≤50ms→100 · 100→85 · 200→60 · 400→30 · ≥800→0（分段线性） |
| 稳定性 S | 0.30 | 每节点测量历史（环形 20 条）+ **burst 丢包率**（2026-07-07 增强）：直连测速每节点串行 3 次独立 TCP 握手，延迟取成功样本中位数（偶数取较小侧）、丢包率 = 失败/3 | `100 × (1 − 平均丢包率) × (1 − 0.5×变异系数)`；无 lossFraction 的老样本按「成功=0 / 整轮失败=1」折算；样本<3 → 70（中性） |
| 带宽 B | 0.15 | `observedPeakDownBps` 被动峰值，拟7天半衰期衰减（当前未实现） | ≥8MB/s→100 · 2MB/s→60 · 0.5MB/s→30 · 无数据→60（中性，不惩罚没轮到的节点） |
| 成本 C | 0.10 | `rateForComparison` | ≤0.5x→100 · 1x→80 · 2x→40 · ≥5x→10 |

**地区**不进打分：`preferredRegion`/`excludedRegions` 保持**硬约束**（先过滤后打分）。
「域名画像 → 地区亲和」维度留到 P3——「哪个地区访问某服务最好」需要数据积累，v1 别拍脑袋。

**域名画像的正确用法**（你想法的核心，我建议这样落）：不是给维度加权，而是给**测量目标**加权——
经代理延迟的探测目标从固定 Cloudflare 改为**你的 Top-3 代理域名**（从 30 天 DomainDailyHistory
按连接数取走 proxy 的域名），`L = Σ(域名权重 × 该域名延迟) / Σ权重`。
延迟维度就天然是「你常用的东西快不快」；带宽被动观测本来就是真实流量，同理免费获得画像属性。

**切换决策（黏性升级，不推倒现有哲学）**：
- 分数滞后：`newBest.score − current.score ≥ 8` **且连续 2 轮成立**才切（幅度+持续双滞后）；
- 当前节点连续 2 次测量失败 → 无条件立即切（可用性 > 稳定）；
- 全量重启路径仍叠加现有 `autoSwitchWorthRestart` 闸；无感热切换路径只用分数滞后。

**UI 原则**：不暴露权重滑杆，只给三档预设——「速度优先 / 均衡 / 省流量优先」
（映射三组权重，省流量档 C 提到 0.30）；节点详情显示分数构成条 + 择优日志写「为什么选它」
（透明度是信任来源，也是宣发差异点）。

## 2. 新增数据结构（唯一的地基工程）

```
NodeMetricsHistory：每节点环形 100 条 {at, latencyMs?, proxiedMs?, lossFraction?}
（P2：20→100，为回放对比实验攒足够长的测量序列；老文件 ≤20 条照常解码、累积到 100 才挤）
lossFraction = 本轮 burst 丢包率（失败/3）；老文件 JSON 无此字段照常解码（Codable 可选）
落盘 node-metrics.json（本地瞬态，不上 iCloud，同 domain-history 待遇）
体量：500 节点 × 100 条 × ~48B ≈ 2.4MB；全在主 App，不碰扩展 50MB 红线
```

**burst 只做直连**：经代理测速不 burst —— 每次都真实走节点发 HTTP，3 倍成本不值当；
经代理只贡献延迟维，不贡献丢包。整轮时长上界 3×5s×节点数/8（并发窗口语义不变），可接受。

## 3. 分阶段（每阶段独立可验收）

- **P1 地基**：NodeMetricsHistory 记录管道 + 稳定性维度 + 打分框架替换
  `bestPreferringLowRate` 内核（外层地区约束/滞后/触发时机全不动），默认均衡档。
- **P2 画像**：Top-3 域名探测目标 + 带宽维度接入 + 三档预设 UI + 「为什么选它」。
- **P3 远期**：地区亲和维度；端侧 AI 动态调权（接你之前的端侧 AI 想法）。

## 4. 竞品对比怎么做（#5）

两条路，先易后难：

**A. 离线回放仿真（P1 数据管道的免费副产品）**：NodeMetricsHistory 积累 ≥1 周后，
用同一份测量序列回放两个策略——「仅直连 ping 最低」（竞品基线）vs 我们的打分——每轮各自选节点，统计：
- 用户加权延迟（对 Top 域名）→ **「提速 X%」**
- 所选节点倍率 × 实际字节 → **「同样用量流量费省 Y%」**
- 切换次数 → **「无谓切换少 Z 次」**

**B. 在线 A/B（自己设备，可选加强）**：诊断页加实验开关，每小时交替策略、对 Top 域名发探测并记录
字节×倍率，7 天自动出报告。

**诚实边界（宣发要守住）**：数字依赖机场质量与个人使用画像——文案写「实测样例：在 N 节点
混合倍率订阅下…」，不做普适承诺；不点竞品名，说「与『仅按 Ping 择优』策略相比」。

## 5. 风险与取舍

- **不做主动吞吐测试**：下载测速烧的是倍率流量（2x 节点测 50MB = 100MB 配额），被动观测够用；
- 探测频率不变（沿用现有 30 分钟档），只是目标更换 → 流量成本几乎不增；
- 打分再好也治不了机场本身抽风——稳定性维度只能「事后避开」，冷启动仍靠延迟。
